## 📖 Overview

The **Project Health Plugin** (`io.github.anyonehub-dev.diagnostics`) is designed to effortlessly plug into massive multi-module codebases without mutating your build graph or pushing unwanted repositories. 

It hooks into the Gradle execution lifecycle to harvest diagnostic metrics and generates a rich `project-health.html` report locally in each evaluated module. 

### Core Philosophy
> [!IMPORTANT]  
> **Read-Only by Design.** This plugin will **never** alter your source code, modify your configuration structures, or fail your build. It exists purely as an observational diagnostic tool.

---

## ✨ Features

### 1. Multi-Language Compiler Warning Aggregation
Modern Android projects consist of Kotlin, Java, and C++ (JNI). Compilers spit out warnings that are easily lost in the terminal scroll. The Health Plugin captures and aggregates:
* **C++** (via CMake / AGP `.cxx/` artifact folders)
* **Kotlin** (via `kotlin-build` reports)
* **Java** (via Javac temp compile directories)

### 2. Dead Code Detection (via R8)
It integrates natively with the Android Gradle Plugin's R8 minification pipeline.
When executing on `release` variants (or any variant with `isMinifyEnabled = true`), it parses the `usage.txt` artifact generated by R8 and computes dead-code metrics directly for your report.

### 3. Dependency Diagnostics
Using robust bytecode scanning and cross-referencing, the plugin evaluates your declared dependencies.
* **Outdated Dependencies**: Async version-check workers ping Maven Central/Google to determine if your declared libraries have newer stable versions available.
* **Unused Dependencies**: Scans `compiledClassesDir` and declared configurations to find dependencies that are pulled into your classpath but whose package namespaces are never actually referenced in your compiled bytecode.

## 🚀 Installation & Application

### 1. Apply via Plugins Block
To apply the plugin, include it in your root `build.gradle.kts` (to apply to all subprojects) or a specific module's build script:

```kotlin
plugins {
    id("io.github.anyonehub-dev.diagnostics") version "1.1.4"
}
```

### 2. Multi-Module Setup (Recommended)
Because the plugin generates reports locally in the applying project's directory, it's highly recommended to apply it via the `subprojects` block at the root level:

```kotlin
// root build.gradle.kts
plugins {
    id("io.github.anyonehub-dev.diagnostics") version "1.1.4" apply false
}

subprojects {
    apply(plugin = "io.github.anyonehub-dev.diagnostics")
}
```

## ⚙️ Configuration

The plugin operates securely out of the box with zero configuration required. However, you can control the async network calls using a Gradle property.

### Network Checks (Dependency Version Lookups)
The dependency diagnostic task spins up async workers to check for library updates. If you are operating in an offline environment (or CI/CD without outbound access), you can disable these checks.

In your `gradle.properties`:
```properties
# Disable network calls for dependency version resolution
healthCheckNetwork=false
```

## 🛠 Usage & Task Execution

All tasks are registered **lazily**—meaning they cost nothing during Gradle's configuration phase. 

### Generating the Report
Simply invoke the primary aggregation task. Because the plugin binds strictly to minified (usually `release`) variants to properly evaluate dead code, you should build the `release` variant of your modules simultaneously:

```bash
./gradlew clean assembleRelease projectHealthReport
```

> [!TIP]  
> Because of fixes introduced in recent versions, the plugin perfectly supports `org.gradle.parallel=true`. If invoked at the root level across a massive multi-module project, every module will independently and safely generate its own `project-health.html` report directly inside its module directory!

### Exploring the Sub-Tasks
If you wish to run individual diagnostic tools without generating the final markdown report, you can invoke the intermediate tasks:
* `./gradlew generateCompilerDiagnostics`
* `./gradlew generateDeadCodeReport`
* `./gradlew generateDependencyDiagnostics`

## 📄 Output Artifact

Upon successful execution, the plugin writes `project-health.html` directly into the module's root directory.

### Example Output Structure
```html

## 🚨 Compiler Warnings (Total: 12)
* **Kotlin**: 8 warnings (e.g. Unchecked casts, Deprecated API usage)
* **Java**: 4 warnings
* **C++**: 0 warnings

## 💀 Dead Code Metrics (R8)
* **Unused Classes**: 14
* **Unused Methods**: 53
* **Unused Fields**: 12

## 📦 Dependency Diagnostics
* **Outdated**: 2 dependencies
  - `androidx.core:core-ktx` (Current: 1.9.0 -> Latest: 1.13.1)
* **Potentially Unused**: 1 dependency
  - `com.google.code.gson:gson:2.10`
```

## 🤝 Contributing

Contributions are welcome! Please ensure that you test any modifications by publishing to Maven Local (`./gradlew publishToMavenLocal`) and verifying the plugin in a downstream consumer project. 

### Publishing to Maven Central
This project uses the Vanniktech Maven Publish plugin. To publish a new version:
1. Bump the `version` inside `build.gradle.kts`.
2. Ensure you have valid Sonatype credentials configured in `~/.gradle/gradle.properties`.
3. Execute:
   ```bash
   ./gradlew publishAndReleaseToMavenCentral
   ```
